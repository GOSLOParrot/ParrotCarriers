# BigIssue: 设计护栏

> 日期: 2026-04-06 初稿 → 2026-04-08 重构
> 性质: 从真实事故中提炼的工程原则，不是操作手册

---

## 一、发生过什么（一句话）

AI 调研从"发现"滑坡为"预设计"，在没有任何代码验证的情况下输出了"冻结"协议 schema，后续所有工作被这些纸上协议锁死，设计在纸上空转了多轮。

**根因**: 协议设计在没有真实代码约束时是空转。

---

## 二、三条硬护栏

### 护栏 1: 代码先于协议

```
❌ 先在纸上定义 ModuleManifest 全部字段 → 然后按字段写代码
✅ 先写能跑通的最小代码 → 从代码中提炼出实际需要的字段
```

**判断标准**: 如果一个协议字段没有对应的消费代码，它就不应该存在。

当前代码中的 `ModuleManifest`、Redis channel 命名、`Envelope` 格式等全部是**候选口径**。它们可以用来指导开发方向，但任何一个字段都可以被实际代码推翻。

### 护栏 2: 不提前收敛

```
❌ "冻结 v1 → v1 追加 → v2 升级" 式的版本管理
✅ 每一轮代码验证后收敛一批，未验证的保持候选
```

**判断标准**: 如果你想写"冻结"二字，先问——有没有可运行的代码证明这个设计是对的？

具体地说：
- Phase 1 代码跑通后收敛 → Bus 层级声明、心跳机制、挂载协议
- Phase 2 代码跑通后收敛 → DSG 接口、Graphiti 分区策略、记忆归属
- 未到对应 Phase 的设计保持"候选"

### 护栏 3: 问题真实 ≠ 方案成立

```
❌ 发现"results 用 Pub/Sub 会丢消息" → 立即设计 Stream + Blackboard 双写方案并固化
✅ 发现问题 → 记录问题 → 写到代码时用最简单方式跑通 → 看实际是否真的丢 → 再决定
```

**判断标准**: 问题可以提前记录，方案必须等代码验证。

## 三、已确认的真实问题（待代码验证方案）

这些问题在架构分析中被发现，**问题本身真实有效**。方案在对应 Phase 的代码中自然暴露：

| 问题 | 会在什么时候暴露 |

## 四、迭代节奏

```
Phase 1 (Bus-first)
  写代码 → 碰到问题 → 用最简方式跑通 → 记录实际选择
  Phase 1 结束时收敛: 模块注册/心跳/挂载的实际协议

Phase 2 (功能叠加)
  在 Phase 1 的实际协议上叠加 → 新问题自然暴露 → 同样方式处理
  Phase 2 结束时收敛: DSG 接口/Graphiti 分区/外部渠道的实际协议

Phase 3+ 
  继续渐进扩展
```

关键区分：
- **模块划分、需求清单、架构拓扑** → 可以在纸上做，但口径是"候选"
- **协议 schema、字段定义、消息格式** → 必须等代码验证后再收敛
