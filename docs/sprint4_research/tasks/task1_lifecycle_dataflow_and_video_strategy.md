# DeepResearch 任务 1：移动端 WebRTC 生命周期的防御性编程与正交视频数据流控制策略

## 1. 你的角色与任务
你是一个资深的移动端实时通信（RTC）架构师和工程调研专家。你的任务是帮我从各大开源社区（GitHub, Reddit, Unity 论坛）、大厂工程博客（Discord, VRChat 等）以及前沿项目中，挖掘**移动端 WebRTC 生命周期防御策略**和**复杂视频数据流控制**的最佳实践。
**请注意：不要向我解释下文的“项目背景”，那是给你用来匹配相似架构和过滤无用信息的。我需要你直接对比优劣、找出突破性优化策略和可能的坑点。**

## 2. 我们的项目背景与架构约束（仅供参考匹配，勿长篇大论复述）
- **技术栈**：Unity 2022.3 + AR Foundation 5.1.x + LiveKit Unity SDK。
- **数据流架构**：借鉴了 Stream Vision Agent (SVA) 的自建管线，后端有 Processor 组件处理 DSG（动态场景图）。
- **视频策略（两个桥墩与正交控制）**：
  - 我们不依赖单一的高清视频流。
  - **桥墩 1（主视频流）**：Unity 推送一条 `ar-camera` 连续视频流给 Gemini Live 消费，默认低码率低延迟。
  - **桥墩 2（补充截帧流）**：按需提取高清画面（`captureSnapshot`），不干扰主视频流。
  - **正交质量门控**：视频的质量（Bitrate/FPS）由后端的 Tool 发送 RPC 指令到前端进行“正交控制”（即：质量切换与连接状态解耦，按需升降档）。
- **当前痛点**：连接脚本缺乏策略，只是测试了连通性。在移动端切后台/锁屏、网络切换时，LiveKit 极易假死。

## 3. 必须调研的核心问题
### 问题 A：移动端生命周期与 WebRTC 的防御性编程
在 Unity 移动端（Android/iOS），当触发 `OnApplicationPause`（切后台/锁屏）或发生 WiFi/4G 网络切换时，优秀的语聊/多人游戏（如 VRChat, Discord 移动端）是如何处理的？
- **对比策略**：切后台时，是主动释放相机/麦克风并向服务器发信令（主动断开），还是硬抗等系统杀进程？切回前台时，是依赖 WebRTC 的 `ICE Restart`，还是直接 `Room.Disconnect` 后彻底重新 `Connect`？
- **收集目标**：这两种策略在移动端真实环境下的成功率对比、优劣势分析，以及具体的 C# 处理逻辑或开源项目参考。

### 问题 B：正交视频质量控制与多路数据流的工程优化
在类似我们的“双桥墩”（连续低画质流 + 按需高画质截帧）和“正交门控”（RPC 动态调控码率）架构中，前沿工程项目是如何优化数据流的？
- **对比策略**：在不中断 WebRTC 连接的情况下，动态修改推流参数（如 LiveKit 的 Simulcast 层级切换 vs 直接替换 Track `ReplaceTrack`）哪种更平滑？
- **收集目标**：社区中处理多路视觉需求（LLM 需要连续低延迟，CV 模型需要单张高清）的突破性架构设计，以及在移动端频繁切换视频质量时可能遇到的坑（如：编码器崩溃、内存泄漏、黑屏假死）。
