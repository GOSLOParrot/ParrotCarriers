# DeepResearch 任务 3：具体 ECP (Embodied Control Protocol) 协议的优秀设计、前沿对比与避坑指南

## 1. 你的角色与任务
你是一个资深的具身智能架构师和通信协议专家。你的任务是帮我深入挖掘**具体的 ECP (Embodied Control Protocol) 设计细节**。
**请注意：不要向我解释下文的“项目背景”。我不需要泛泛的理论验证，我需要你找出前沿开源项目或研究中，具体的 JSON/Protobuf 协议定义结构、字段设计，以及他们在处理状态同步时的具体坑点。**

## 2. 我们的项目背景与架构约束（仅供参考匹配，勿长篇大论复述）
- **技术栈**：Python 后端 (Gemini + 任务调度器 + BlackBoard + py_trees + DSG/Graphiti) <--> Unity 2022.3 前端 (Animator, AR)。
- **当前目标**：我们正在将后端的 DSG/任务调度器与前端的通信协议升级为 **协议 V2 (ECP)**。目前已经明确了需要“双重防御（行为树拦截+前端微锁）”和“带时间戳的延迟补偿”。
- **需求**：我们需要具体的设计参考，比如一个标准的 ECP 消息包长什么样？如何定义连续动作与离散动作？

## 3. 必须调研的核心问题与自由探索广度

### 广度搜索与自由探索目标 (Free Exploration)
**请在深入具体问题之前或同时，保持广泛的视野进行自由探索。**
- **探索目标**：不要被下文的具体问题完全局限。请在具身智能通信协议（Embodied AI Protocols）、机器人中间件（ROS2, Viam）、以及多模态大模型（VLM/LLM）与物理世界交互的最新开源项目中，寻找**任何突破性的、非传统的通信与状态对齐方案**。
- **关注点**：如果社区有比我们当前认知（如带时间戳的 RPC 指令流、状态同步）更优雅的解法，请务必将其纳入报告，并说明其对我们架构的潜在启发。

### 问题 A：前沿 ECP 协议的具体结构与字段设计
在 Stanford Mobile Aloha, Google RT-2, 或其他优秀的开源具身智能/虚拟人项目中，他们是如何定义控制协议的数据结构的？
- **收集目标**：
  1. 找出 2-3 个具体的协议 Payload 示例（如 JSON 或 Protobuf 结构）。
  2. 他们是如何在协议中区分“离散动作（如：播放跳舞动画）”和“连续状态（如：保持注视目标、跟随移动）”的？
  3. 协议中除了 `timestamp`，还有哪些关键的元数据字段（如 `priority`, `interruptibility`, `expiration`）被证明是必不可少的？
  4. **前沿解法收集**：例如基于流式 Token 的动作预测、基于物理引擎预测的延迟补偿等非传统方案，他们是如何在协议层实现的？

### 问题 B：状态对齐 (State Reconciliation) 与自建管线的时间轴对齐坑点
在使用自建的 ASR/TTS 管线（而非 Gemini Live 原生音频）时，后端提取的文本、生成的语音，如何与前端的视觉节点（Sighting）在时间轴上精确对齐？
- **收集目标**：
  1. 前沿项目是如何在协议层解决“后端 LLM 看到画面 A 并生成文本，但前端已经渲染到画面 B”的时间轴错位问题的？
  2. 谁来负责向系统广播 `SPEAKING` / `LISTENING` 的状态？（是 TTS 引擎发事件，还是前端检测到音频流发事件？）列出这两种方式的优劣和常见坑点。

## 4. 输出格式与要求
一份 Markdown 调研报告，包含：
1. **具体的协议 Payload 示例**：展示前沿项目中的 JSON/Protobuf 结构，并解释关键字段的作用。
2. **连续与离散动作的协议设计对比**：说明在协议层如何优雅地处理这两类动作的下发与取消。
3. **时间轴对齐与状态广播避坑指南**：针对自建 ASR/TTS 管线，给出具体的时间戳对齐方案和状态广播的最佳实践。
