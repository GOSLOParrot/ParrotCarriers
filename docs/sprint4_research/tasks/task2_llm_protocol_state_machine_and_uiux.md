# DeepResearch 任务 2：具身智能/AR伴侣的前端状态机设计、LLM 控制协议与优秀 UI/UX 拆解

## 1. 你的角色与任务
你是一个资深的游戏交互设计师（UI/UX）和机器人控制协议专家。你的任务是帮我从优秀的独立游戏、AR App、聊天软件中提取**界面布局与加载流程**的灵感，并从前沿的具身智能（Embodied AI）项目中挖掘**LLM 与前端状态机交互的通信协议**最佳实践。
**请注意：不要向我解释下文的“项目背景”。我需要你对比前沿方案与我们的计划，找出设计要点、坑点，并提供大量优秀的设计案例。**

## 2. 我们的项目背景与架构约束（仅供参考匹配，勿长篇大论复述）
- **技术栈**：Unity 2022.3 (前端) + Python (后端)。
- **控制架构**：
  - **后端**：AI (Gemini) + 任务调度器 + 黑板模式 (Blackboard) + 行为树 (Behavior Trees, py_trees)。
  - **前端**：Unity Animator 状态机（处理飞行、降落、思考、说话等动作）。
  - **通信协议**：后端通过 LiveKit RPC 指令（如 `{"type": "anim_cmd", "animation": "dance"}`）异步控制前端。
- **当前痛点**：缺乏正式的 App 启动流程和 UI 布局；后端指令与前端状态机之间可能存在指令冲突、状态不同步（Desync）和动作僵硬的问题。

## 3. 必须调研的核心问题
### 问题 A：LLM <-> 机器人/前端状态机的控制协议与防冲突策略
在前沿的机器人控制、虚拟偶像或具身智能工程中，异步的 LLM 后端（带行为树/黑板）是如何与同步的前端状态机（Unity Animator）进行可靠通信的？
- **对比策略**：我们的“RPC 纯指令流”策略 vs 业界前沿的“状态同步 (State Sync)”或“目标驱动 (Goal-driven)”协议。
- **收集目标**：
  1. 当 LLM 连续下发冲突指令（如：正在跳舞时要求起飞），优秀的协议是如何在后端（行为树拦截）和前端（状态机缓冲队列）进行双重防御的？
  2. 这种 RPC 指令控制模式下，最容易踩的坑是什么（如：网络延迟导致动作与语音对不上、状态机死锁）？前沿工程是如何解决的？

### 问题 B：优秀 AR / 跑图 / 相机类游戏的 UI 布局与启动流程 (Onboarding)
市面上优秀的独立游戏、AR App（如 Pokémon GO, Peridot）、照相机游戏或创新聊天软件，是如何设计 UI 布局和启动流程的？
- **收集目标（大量案例拆解）**：
  1. **启动与加载流程**：打开 App 的第一个画面是什么？如何丝滑地掩盖 LiveKit 连线、AR 平面扫描和权限请求的等待时间？（寻找 3-4 个优秀案例的流程拆解）。
  2. **UI 布局与互动设计**：在以相机画面为主的 AR 场景中，主菜单放哪里？玩法入口（如：便签抽屉、语音状态指示、切换相机模式）怎么布局最符合单手人体工学且不遮挡 AR 角色？
  3. **状态可视化**：优秀游戏是如何通过 UI 或角色微表情（如思考气泡、发呆动画）来掩盖网络卡顿或 LLM 推理延迟的？

## 4. 输出格式与要求
一份 Markdown 调研报告，包含：
1. **控制协议对比与避坑**：对比我们的 RPC 指令流与前沿具身智能协议的优劣，列出 3 个可能导致“状态机死锁或表现撕裂”的坑点及前沿解法。
2. **优秀启动流程 (Onboarding) 案例库**：详细描述 3 个优秀 App 的冷启动到进入主玩法的流程设计（重点关注如何处理权限和加载掩盖）。
3. **AR/相机游戏 UI 布局参考**：总结 3 条以相机为主视角的移动端 UI 布局黄金法则（如热区分布、非侵入式 UI），并附带具体游戏的设计说明。
