## M0 开场：项目解决什么问题

各位老师好，我这次答辩介绍的是“AR+生活助手与智能提醒”系统。

这个项目不是单纯做一个聊天机器人，也不是只做一个日程提醒工具。我的目标是让助手进入真实的 AR 场景以后，能够理解用户当前看到什么、正在做什么、有哪些信息可以作为依据，并在合适的时候主动协助用户。

传统助手通常依赖文本输入，或者只按固定时间提醒。这样的问题是，它知道“时间到了”，但不一定知道“用户现在处在什么场景”。所以这套系统重点解决的是：怎么把语音、视频、照片、日程、笔记和历史记忆组织到一起，让 Agent 有一个持续更新的场景上下文。

这一部分我想先建立一个判断：我做的不是单点功能，而是一个面向 AR 场景的 Agent 原型。

## M1 背景知识：系统需要哪些输入

在进入架构之前，我先用几页图，把后面会反复出现的几个输入源说明白。这里不展开细节，只让老师知道它们是什么、为什么会进入系统。

第一类是 LiveKit 和 SVA。LiveKit 可以理解为实时音视频和数据通信的底座，它负责把语音、视频、参与者和数据消息放在同一个实时会话里。SVA 这里主要指一种 Processor 思路：视频流不只是直接给大模型看，也可以先经过处理器，变成结构化的视觉结果，再交给 Agent 使用。

第二类是 nanobot。这里我把它放在后台任务这一侧来理解。对于日程处理、资料整理、消息检查这类慢任务，前台对话不应该一直等待。系统会在确认之后，把任务交给后台 Worker 或 nanobot gateway 处理。

第三类是 Google Calendar。它提供的是用户真实生活里的时间上下文。智能提醒不只需要知道“提醒什么”，还要知道“什么时候提醒”“是否和已有安排冲突”。

第四类是 Obsidian。它是本地 Markdown 笔记和日记工具。在这个项目里，它代表用户长期可编辑的个人知识来源。

最后是更多 CV 扩展输入，比如 YOLO、SAM2、DINOv2 和 ConceptGraph。这里不是说项目已经完整实现了这一整条视觉流水线，而是说明一个方向：视觉信息可以从原始画面，逐步变成对象、特征和关系，最后进入场景记忆。

这一分钟的目的很简单：先让老师认识这些名词。后面讲架构时，它们就不是突然冒出来的技术栈了。

## M2 总体架构：这些输入怎么组织起来

现在把这些输入放回系统里看。

整体上，前端是 Unity AR 应用，负责相机、麦克风、AR 交互和 3D 助手展示。LiveKit 是实时通信中枢，承载音视频、RPC 和 DataChannel。后端 Brain Agent 负责理解用户意图、调用工具和组织上下文。DSG 负责运行时的场景工作记忆，Graphiti 负责更长期的图记忆。Scheduler 和 nanobot 负责后台任务协作。

所以这套架构不是把技术简单堆在一起。它真正要做的是把不同来源的信息统一成几个关键对象：Observation、Ref、Intent、Task 和 Episode。

简单说，Observation 是系统看到或收到的一条观察；Ref 是可以追踪的证据或引用；Intent 是前台正在处理的用户意图；Task 是需要后台执行的任务；Episode 是值得长期保存的一段情景记忆。

后面我会用几个流程说明这些对象怎么流动。

## M3 核心设计一：LiveKit、SVA 和 Context 注入

第一个核心设计是：实时视频和视觉信息怎么进入 Agent。

最直接的办法，是把视频流直接交给大模型。但这样不够可控，也不一定能留下清楚的证据。因此我借鉴 SVA Processor 的思路，在实时音视频流旁边增加处理器。处理器可以按受控频率处理视频帧，把结果变成结构化信息，再注入到大模型上下文，或者写入 DSG 记忆层。

这里 LiveKit 的作用不只是“传视频”。它提供了几类通道：Track 用来承载音视频流；DataChannel 用来传状态和事件；RPC 用来让后端触发前端动作。

这样一来，视觉信息就不只是模型临时看一眼，而是可以变成可追踪的 Observation 或 Ref，进入后面的记忆流程。

这一页我想表达的是：SVA 在这里不是一个玄学名词，而是一种让视频流变成结构化上下文的处理方式。

## M4 核心设计二：ECP 和前台动作闭环

第二个核心设计是前台动作的状态同步。

在 AR 系统里，后端不能只说“我已经执行了”。比如用户让助手做一个前台动作，后端会先把它识别成 Intent，再通过 LiveKit RPC 发给 Unity。Unity 执行以后，会返回 ACK。后端再把这个结果写入 Blackboard，作为共享状态。

这个过程就是 ECP 闭环要解决的问题：模型认为执行了，和前端真的执行了，必须对得上。

如果前端拒绝、超时或者执行失败，后端应该知道，然后给用户正确反馈。否则系统看起来像在回应，实际上前端状态已经不同步了。

这里我会谨慎一点讲：当前系统已经把 RPC 结果镜像到 Blackboard，形成状态闭环；但不夸大成所有命令都已经有完全统一的新 ACK 协议。

## M5 核心设计三：Reflex、Intent、Task 和 nanobot

在行为调度上，我把动作分成三层：Reflex、Intent 和 Task。

Reflex 是最快的一层，适合本地手势、急停、状态变化这类低延迟动作。Intent 是前台用户明确发起、需要状态回执的动作，比如拍照、切换模式、让角色执行动作。Task 则是耗时的后台任务，比如日程处理、消息检查、资料整理。

这里我用“改日程”说明 Intent 和 Task 的区别。用户说“帮我把会议改到晚上”，系统首先生成日程变更草稿。这个阶段还属于 Intent，因为系统需要理解、确认，并让用户知道将要改什么。

确认之后，真正的日程执行请求才升级成 Task，比如 `calendar_patch`。它会交给 Scheduler，再通过 Redis Stream 派发给 nanobot Worker 或真实 nanobot gateway。完成后，结果再回流给前台。

这样设计的好处是，前台对话不会被慢任务卡住，后台任务也不会和用户正在感知的 AR 动作混在一起。

## M6 核心设计四：DSG、Graphiti 和触发器协议

第三个重点是记忆组织。

这里的 DSG 不是单纯的机器人地图，而是运行时工作记忆。它负责接收语音、视频、照片、日程、Obsidian 和工具结果，把它们组织成可以追踪的 Observation 和 Ref。

Graphiti 则更适合长期记忆。它保存的是带时间、来源和实体关系的信息，也就是 Episode、Entity 和 Fact。

在这个基础上，我设计了触发器协议。触发器不是某一个固定提醒功能，而是一套统一的事件处理机制。事件发生以后，系统可以选择提交 Observation、暂存 Ref、请求归档 Episode、生成计划、派发后台任务，或者通知前台。

这样，Photo Awareness、Graphiti 预加载、主动提醒这些功能，就不是散落的逻辑，而是同一套 TriggerOutcome 的不同结果。

这里也需要保守表述：Graphiti 和 Obsidian 的长期治理还没有完全结束，目前可以说已经建立了原型链路、分区和 UUID 绑定思路。

## M7 核心设计五：L1.5、多源 Ref、UUID 和拍照流程

最后一个核心设计是多源 Ref 和 UUID。

我用拍照流程来说明。用户在相机模式下按下快门后，系统不会直接把图片塞给大模型。它会先产生一个轻量预览事件，让后端知道发生了一次拍照；完整图片再异步上传，作为真正的图片资产保存下来。

后端收到这些信息后，会创建 PhotoNode，把图片暂存为 PHOTO 类型 Ref，并绑定到对应的路径和标识。这样做的意义是，照片不再只是一次临时输入，而是变成了可追踪的证据。

同样的思路也可以用于语音、日程、笔记和外部工具结果。不同来源的信息通过 Ref 和 UUID 绑定起来，后面才能检索、确认、升级，或者归档到 Graphiti。

这里不能说拍照以后系统就自动得到可靠的 ObjectNode。更准确的说法是：照片先成为证据入口，后续再做识别、确认和长期记忆归档。

## M9 总结

最后总结一下。

这个项目完成的不是一个单点功能，而是一条面向 AR 场景的可追踪数据流：多模态输入进入系统，前台动作通过 ECP 保持状态闭环，短期信息进入 DSG 工作记忆，长期信息归档到 Graphiti，耗时任务交给 Scheduler 和 nanobot 后台处理。

创新点可以概括成四个方面。

第一，多源输入通过 Ref 和 UUID 进入统一上下文。第二，实时视频流不仅可以给大模型看，也可以通过 Processor 变成结构化记忆。第三，ECP 和 ACK 让前台动作有状态闭环。第四，Reflex、Intent、Task 三层让前台交互和后台任务分工更清楚。

目前系统仍然是原型，后续还可以继续完善视觉稳定性、Graphiti 记忆治理，以及更多外部模块接入。
