# 26 · 算力任务分配、降级策略与数据职责愿景

> 生成日期: 2026-03-18
> 状态: 架构愿景与高层需求（非最终实现的硬性规范，需在后续开发中逐步演进、验证和审计）
> 目的: 明确 YOLO-World 的插件化用法，梳理跨设备（手机/PC/云端）的算力分配与降级策略，并界定大架构下数据存放的职责边界。

---

## 一、YOLO-World 插件的定位与用法澄清

在之前的讨论中，YOLO-World 的定位有所跳跃。现在明确，它应被设计为一个**“解耦的语义探测插件 (Semantic Probe)”**，兼具通用探测与专用检索的双重特性。

### 1. 核心用法：基于记忆提示词的预加载发现
- **机制**：当场景切换或加载时，系统从 `Graphiti` 的记忆中拉取该空间（或用户近期关注）的物体文本列表（如：["红框眼镜", "马克杯", "黑色键盘"]）。
- **执行**：将这些文本作为 Prompt 喂给 YOLO-World，让其在视野中进行定向探测。

### 2. 在“满血模式 (A10 GPU 在线)”下的作用
在云端 GPU 充足时，SAM2 是全分割的主发现路径（负责精确追踪和轮廓生成），此时 YOLO-World 不抢主导权，而是发挥两大辅助作用：
- **交叉验证 (提供证据)**：SAM2 找到了一个未知的 Mask，此时 YOLO-World 的文本探测框如果与 Mask 重合，就能立刻提供一个高置信度的语义标签，加速 `EvidenceAccumulator` 的确认过程。
- **主动搜索 (加速发现)**：当 GOSLO 被问到“我的红笔在哪？”时，直接把“红笔”发给 YOLO-World，它能比盲目的 SAM2 全分割更快地给出一个候选区域，随后再让 SAM2 和 DINOv2 去该区域做精确裁切和特征匹配。

### 3. 在“降级 / 哨兵模式”下的作用
- 当 A10 掉线，或者部署在只有 CPU/核显的用户笔记本上（作为 DSG Sentinel 哨兵）时，跑不动 SAM2。
- 此时 YOLO-World（或更轻量的 YOLOv8/v10）就“转正”成为该设备上的视觉主力。只提供粗略的 BBox 和标签，通过 Redis 将这些“低权重证据”汇报给云端大脑。

### 4. 架构设计原则
- **分开设计，作为插件**：不应与 SAM2 强绑定在一个类里。它是一个独立订阅视频流的总线模块/线程，通过总线输出 `BBox + Label + Score`，由后端的 DSG 逻辑层来决定如何融合这些数据。

## 二、算力任务分配与动态降级策略 (Compute & Degradation)

我们的硬件生态是一个异构池：**手机 App (必须)** + **电脑哨兵 (可能有)** + **云端服务器 (必须有 CPU，可能无 GPU)**。任务必须根据算力和延迟要求合理卸载。

### 1. 算力任务池与最佳分配
| 任务类型 | 延迟容忍度 | 首选计算设备 | 理由与机制 |
| :--- | :--- | :--- | :--- |
| **VAD 与关键词唤醒** | 极低 (<100ms) | **手机 App 端** | 在音频推流前本地处理，避免无效音频上云，节省带宽。 |
| **基础姿态与平面检测** | 极低 (<50ms) | **手机 App 端 (ARCore)** | 必须依赖本地原生 ARCore 零延迟返回 6DoF 和追踪状态。 |
| **动作指令执行 (动画)** | 低 (<200ms) | **手机 App 端 (Unity)** | 云端只发 `fly_to` 这种高层语义 RPC，动画机在手机端渲染。 |
| **轻量级特征/物体发现** | 中 (1~2s) | **电脑哨兵 (YOLO)** | 利用电脑的闲置 CPU/核显，分担云端压力，或提供多视角的辅助镜头。 |
| **主视觉链路 (SAM2+ReID)**| 中 (1~2s) | **云端 GPU (A10)** | 算力大户，必须依靠云端专用显卡维持 15-30fps。 |
| **高阶思考与长程对话** | 高 (2~5s) | **云端 CPU (Gemini/Brain)** | 逻辑中枢，处理大语言模型、上下文组装。 |
| **图谱维护与长程任务** | 极高 (>10s) | **云端 CPU (Nanobot)** | 后台离线异步处理。 |

### 2. 梯级降级策略 (Graceful Degradation)
架构必须具备弹性，当某一层算力不可用时，系统不应崩溃，而是降低智力水平：
- **Level 0 (满血感知)**：云端 GPU 在线。SAM2 实时追踪 + DINOv2 精准识别 + YOLO 语义辅助。鹦鹉具备完美的 3D 空间感。
- **Level 1 (GPU 离线 / 抢占丢失)**：只剩云端 CPU + 手机。关闭 SAM2/DINOv2。**降级方案**：以 1fps 的频率将视频帧直接传给 Gemini API（纯多模态大模型视觉）。鹦鹉失去精确的 3D 坐标追踪，退化为“看图说话”的聊天机器人。
- **Level 2 (云端网络极差)**：云端断联。**降级方案**：鹦鹉进入休眠/本地挂机动画状态，停止环境分析，直到重连。

## 三、数据存放职责与模块交互愿景 (Data & Interaction)

这部分界定“复杂任务处理”时的通信边界。核心法则是：**不能因为副手（Nanobot）在做重活，就阻塞了前台（GOSLO）的交互。**

### 1. Nanobot 交互策略的解耦
- **不强制绑定 py-trees**：实际开发中，不一定非要用复杂的 `py-trees` 子树去硬连 Nanobot。它可以只是一个监听特定 Redis Channel 的独立后台进程（Worker）。
- **异步与状态感知**：当触发复杂任务（如整理过去一周的记忆、搜索一份资料）时，GOSLO 下发指令后立刻继续当前的对话。
- **轻量级信息同步**：GOSLO (Brain Agent) 只需要了解 **“摘要与元数据”**（小负担信息）。例如，Nanobot 把“正在整理文档 [2/5]”的状态写在 Redis 的某个 Key 里。GOSLO 的提示词里只需注入这个状态字典。当用户问“猫猫整理得怎么样了”，GOSLO 瞄一眼状态就能回答，完全不阻塞当前脑力。

### 2. 数据存放与指责边界
为了防止系统越来越卡，不同类型的数据必须放入对应的容器中：

| 数据类型 | 存放位置 (职责容器) | 生命周期 | 消费者 |
| :--- | :--- | :--- | :--- |
| **即时上下文与状态 (小负担)** | `Redis Blackboard` / `State Keys` | 会话级 (随用随弃/覆写) | GOSLO, 调度器, UI |
| **多模态物理文件 (照片/音频/预制体)** | `Google Drive` / `Obsidian` / `S3` | 永久存留 (SSOT兜底) | 外部用户, Nanobot 整理用 |
| **实体关系与事件逻辑 (记忆)** | `Graphiti (Neo4j)` | 长期 (随时间衰减/归档) | GOSLO (提问查询), Nanobot (重组) |
| **向量特征 (视觉 ReID / 文本嵌入)** | 专属向量数据库 (待定如 Qdrant) | 长期 | CV Flow Worker (DINOv2 等) |
| **异步任务队列** | `Redis Stream` / `List` | 任务级 (完成即删) | Nanobot (执行者) |

**架构约束总结**：前台 GOSLO 只消费经过“浓缩和整理”的轻负担数据（状态词典、Graphiti 摘要）；重负担数据（视频流、大文件读写、全量图谱遍历）必须交给后端的 CV Worker 和 Nanobot Worker 异步处理。
